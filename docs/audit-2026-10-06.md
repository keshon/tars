# TARS project audit

> Historical audit of revision `06f636d`, followed by the implementation
> follow-up near the end of this document. The findings and validation below
> describe those revisions, not today's open issues or dependency versions.
> Current behavior is documented in [the CLI reference](cli.md),
> [terminal guide](tui.md), and [architecture](../ARCHITECTURE.md).
> Source links below are portable checkout links; old line locations have
> moved as the implementation changed.


TARS has a strong core and an inconsistent operational contract. Keep the Go engine, package boundaries, fresh-context workers, and independent eval criteria. Put the next development effort into permissions, cancellation, verification, and reversible changes before adding more tools or model-specific nudges.

It is a useful supervised personal agent. This revision does not yet justify trusting unattended runs with a valuable dirty working tree. The limiting factor is integration correctness, not whether the implementation was written with Claude or Muse Spark.

## Scope and evidence

Reviewed revision: `06f636da005db3e5e1ad7fbda416895e6da1fd61`, 6 October 2026. Host: Windows amd64, Go 1.26.4. The working tree was clean at the start.

Coverage includes the CLI, RPC server, API session, TUI state and input handling, agent loop, role construction, permissions, mission planning and checks, backend transport, file and network tools, MCP, persistence, snapshots, eval harness, CI, and documentation. Findings distinguish targeted reproductions from source inspection.

Verification:
- `go test ./...`: passed.
- `go test -race ./...`: passed on Windows.
- `go vet ./...`: passed.
- `go build ./...`: passed.
- `go run ./cmd/eval -dry`: 16 probes validated.
- Nine temporary audit tests reproduced the reported behaviors; the policy test exercised two separate bypasses.
- `govulncheck` failed with five reachable Go standard-library advisories for the installed toolchain.

The nine reproductions are preserved in [audit-reproductions.txt](audit-reproductions.txt). They assert existing bugs: their PASS means the bug was reproduced. Temporary test files were removed from the production packages. No implementation was changed.

This is a code and deterministic behavior audit. No live model evaluation, inference throughput measurement, Linux runtime test, or interactive visual TUI session was performed. Model quality on either of your GPUs remains an empirical question. The screenshot was not visually reviewed: the pixelita inspection tools were unavailable. The canvas skill's managed workspace directory was not available for this project, so this review is delivered as a repository document.

P1 means fix before trusting unattended work; P2 means a material correctness, usability, or maintenance issue; P3 means lower-priority improvement. None of these findings assumes that the advertised workspace guard is a sandbox.

## What is good

**The architectural center is well chosen.** One loop behind small `llm.Client` and `Tool` interfaces is easier to reason about than a collection of model-specific orchestrators. Backend quirks sit in dialects, and concrete tools sit outside the agent package. Import-layer tests make those boundaries more than a diagram.

**Capabilities are usually enforced structurally.** Planners and inspectors do not receive file-writing or shell tools, and subagents do not receive delegation. This is stronger than instructing a model to behave. Central role constructors reduce configuration drift, although mission wiring currently defeats part of that benefit.

**The design addresses real weak-model failures.** Exact-match patches reject ambiguity; native move operations preserve bytes; malformed and truncated calls are distinguished; loops have budgets; output is bounded before entering context; errors remain visible to the model; and recoverable leaked calls still go through the normal execution path. These are useful engineering decisions, not cosmetic agent features.

**Mission contexts are isolated from previous transcripts.** Ledger-derived seeds prevent an exploratory worker's history from consuming every subsequent worker's context. Distinguishing infrastructure interruption from a failed task also avoids spending repair budgets on a dead backend.

**The eval concept is sound.** Frozen workspace, trace, and answer criteria are independent of the model's chosen mission checks. Throwaway fixtures, recorded model metadata, repeat runs, overflow injection, and platform-specific skips are good foundations.

**The TUI is more considered than a thin log viewer.** Tool calls and results are paired by ID, long output can be collapsed, scrolling remains sticky only when appropriate, permission previews explain the proposed action, and rejection notes let the operator redirect the model. Estimated token usage is visibly marked.

**The project uses Go sensibly.** Small interfaces, concrete tool types, explicit constructor configuration, embedded prompts, error wrapping, standard-library-first implementation, build-tagged OS handling, and modest dependencies are appropriate. There is no reason to rewrite the project in another language.

## Findings to fix first

### 1. P1 Permission policy is optional at execution time and explicit deny can be overridden

Reproduced. In [tool.go](../internal/agent/tool.go), policy evaluation occurs only inside `if BeforeToolCall != nil`. Without a gate callback, both Ask and Deny calls execute. This contradicts the documented contract that Ask without a gate degrades to Deny.

With a callback installed, both Ask and Deny are sent to it, and the callback's return replaces the policy verdict. An explicit `-deny` can therefore become an approval question and execute after a yes answer. This is different from a bypass through shell syntax: the harness itself fails to enforce its policy.

The audit test configured an all-Deny policy and a harmless tool. It executed with no hook, and also executed with a hook returning Allow.

**Fix:** evaluate policy unconditionally. Deny is terminal; Ask invokes a gate and denies if none exists; Allow proceeds. Test this matrix through CLI, API, mission, TUI, and delegated roles.

### 2. P1 Mission mode drops permissions and other runtime configuration

Source-confirmed. [missionParams](../cmd/agent/main.go), [runMission](../cmd/agent/main.go), and [Runner.env](../internal/mission/phases.go) omit Policy, Gate, MCPTools, BackendKind, and several observer/model options carried by direct mode.

A user can supply `-deny run_shell=*`, enter mission mode, and get workers built without that override or a tool gate. Default policy is reconstructed by roles, then finding 1 means it is not enforced. Because CLI auto-mission triggers from filename mentions, the loss can happen without explicitly selecting mission mode.

MCP discovery also occurs after the CLI mission branch, so supplied MCP integrations do not become mission capabilities.

**Fix:** pass one shared run environment through every execution path. Make intentional differences explicit. Add an entry-point test proving the same denied operation stays denied in direct and mission runs.

### 3. P1 Public URL validation does not enforce the network destination

Reproduced for redirects. [webfetch.go](../internal/tools/webfetch.go) validates the initial URL and then uses the default HTTP client. [fetch_raw.go](../internal/tools/fetch_raw.go) has the same design. There is no redirect check or dial-time resolved-IP check.

The reproduction returned a 302 from an allowed public-looking URL to `127.0.0.1`; the transport was called for loopback and its private body was returned. No real intranet was accessed. Source inspection also shows that a dotted hostname resolving to a private address is not rejected at dial time.

This contradicts the network boundary promised in SECURITY.md. Inspectors and planners receive these tools, so shell removal does not eliminate this exposure.

**Fix:** share a policy-aware transport, validate redirects, and validate the actual addresses used to dial. Define proxy behavior deliberately. Test redirects, DNS-to-private resolution, and address changes between validation and connection. Go's [HTTP client documentation](https://pkg.go.dev/net/http#Client) describes the default redirect behavior.

### 4. P1 Verification commands inherit credentials that normal shells scrub

Reproduced with a synthetic sentinel. [RunShellCommand](../internal/mission/checks.go) sets the directory and calls CombinedOutput without setting a scrubbed environment. Normal `run_shell` does scrub it.

Mission shell checks are model-generated, so this is a separate execution path through which a model can access API keys in the process environment. The audit set only `TARS_AUDIT_API_KEY=audit-sentinel`; the check shell printed that sentinel. No real key was read.

**Fix:** use a shared process runner with consistent environment, output limits, deadlines, and process-tree cleanup. Apply it to user verification commands and model-generated checks.

### 5. P1 Revert does not restore the pre-run workspace

Source-confirmed. [Revert](../internal/snapshot/snapshot.go) runs `git checkout -- .`; it never consumes the snapshot captured by Track.

This discards pre-existing unstaged changes along with agent changes. It leaves generated untracked files in place. It restores tracked content from the index, whereas the CLI and docs say HEAD. With staged changes, that distinction is observable.

Track saves a diff and an untracked name list, not a complete checkpoint of tracked, staged, and untracked content. A saved diff is useful evidence but is not a dependable undo mechanism.

**Fix:** define rollback as restoring a named pre-run checkpoint. Preserve index state and untracked bytes, scope restoration to the run, and preview it. Until implemented, name the existing operation as discarding unstaged tracked changes rather than reverting an agent run.

### 6. P1 Successful verification can become stale before completion

Reproduced. [finish.go](../internal/agent/finish.go) latches `verifiedOnce`. Later tool mutations do not invalidate a successful check.

The audit ran a mutation, reached a PASSED verification, ran another mutation, and finished. The verification callback ran once, before the last edit.

**Fix:** associate verification with a workspace revision or mutation generation. Any subsequent potentially mutating operation invalidates the result. Require a current verdict at completion and include its command and revision in the report.

### 7. P1 RPC cancellation cannot reliably release permission and plan gates

Source-confirmed. [permissionGate](../cmd/agent/main.go) and [mission plan approval](../cmd/agent/main.go) suspend on `context.Background()`. [roles.Env.gate](../internal/roles/roles.go) discards the loop context because Env.Gate has no context parameter.

The RPC cancel method cancels the run, but these waits do not observe that cancellation. EOF cancellation has the same limitation. EOF handling also checks HasPending only once; a run that reaches a gate after that check has no remaining input source.

**Fix:** propagate the run context through gate interfaces. Mark the transport closed and reject future gate requests after EOF. Test cancellation and EOF both before and after each gate opens.

### 8. P1 TUI interruption can mix old and new runs

Reproduced as a deterministic state sequence. [update.go](../internal/tui/update.go) cancels and immediately sets stDone, enabling a new turn before the old worker exits. [doneMsg handling](../internal/tui/update.go) has no run identifier and unconditionally replaces state and answer.

The reproduction interrupted a run, modeled a new active turn, and delivered the old completion message. The new active state became done and its answer became the old answer. Old step and tool events are also untagged.

There is a related context problem: [model.go](../internal/tui/model.go) captures the original runCtx in the permission hook, while startRun creates new contexts. startRun immediately calls the original cancel function before creating a new context, so the gate can be bound to an already-cancelled context from the first task onward. Later turn cancellation also targets a different context from the gate.

**Fix:** add run IDs to completions and events, discard stale events, and retain a stopping state until the worker drains. Bind gates to the current run. Stress-test rapid stop, follow-up, new chat, and permission transitions.

### 9. P1 The installed Go toolchain has reachable vulnerability advisories

Scanner-confirmed, not an exploit demonstration. `govulncheck` identified five reachable advisories in Go 1.26.4:
- [GO-2026-6218](https://pkg.go.dev/vuln/GO-2026-6218): URL path-resolution resource usage; fixed in 1.26.6.
- [GO-2026-6090](https://pkg.go.dev/vuln/GO-2026-6090): TLS post-handshake message limits; fixed in 1.26.6.
- [GO-2026-5972](https://pkg.go.dev/vuln/GO-2026-5972): ASN.1 recursion limits; fixed in 1.26.6.
- [GO-2026-5856](https://pkg.go.dev/vuln/GO-2026-5856): TLS ECH privacy issue; fixed in 1.26.5.
- [GO-2026-5026](https://pkg.go.dev/vuln/GO-2026-5026): Punycode label handling; fixed in 1.26.6.

Reachability does not establish that every exploit precondition applies to TARS. It does establish that the current local build fails the project's own vulnerability-check criterion.

**Fix:** rebuild with a patched supported Go toolchain and rerun the scan. This is a build-environment issue; changing go.mod dependencies alone does not replace the compiler's standard library. CI already has a vulnerability job.

## Other material findings

### 10. P2 Incomplete SSE responses are treated as complete model responses

Reproduced. [stream.go](../internal/llm/stream.go) ignores malformed JSON chunks and accepts clean EOF without requiring a finish marker or DONE. The reproduction sent one content delta and closed the body: Stream returned text with no error and an empty finish reason.

The loop rejects explicit `length`, but this incomplete response can enter the ordinary finish path. Partial tool arguments can also reach repair logic.

**Fix:** distinguish complete responses from interrupted streams. Require a supported terminal signal, report malformed/error frames, and ensure incomplete tool arguments cannot execute. Retry only when the execution semantics are safe.

### 11. P2 Direct mode can accept a false file-completion claim

Reproduced using default finish behavior. [finish.go](../internal/agent/finish.go) enforces zero-write refusal only when VerifyOnZeroWrites is set. Interactive does not set it; the optional verify command is absent by default.

A scripted model said “I created notes.txt”, received the verification nudge, then repeated the claim. The run returned success with zero mutations.

The direct mode checkpoint often measures only tool-call counts and gives the model another instruction. That is useful fault tolerance, but it does not support the broad README claim that completion is always measured mechanically.

**Fix:** expose separate task outcome states: completed and checked, completed with limited evidence, blocked, and failed. For explicit file-effect claims, require file evidence or return an unverified outcome. Keep read-only tasks valid without requiring arbitrary writes. Mission checks also need honest labeling: existence and substring checks prove much less than functional correctness.

### 12. P2 File-change reporting misses shell and MCP changes

Source-confirmed. [tool.go](../internal/agent/tool.go) collects mutation paths only for named built-in file tools and parses successful delegate envelopes. A successful `run_shell` command that writes a file is not counted as a filesystem mutation; MCP and background writes also have no general discovery mechanism.

The [session-end sweep](../internal/api/session.go) claims to cover these channels, but receives only a.MutatedPaths. It cannot scan changes absent from that list. Shell-only workers can encounter zero-write refusals even when they changed files.

**Fix:** measure workspace deltas across the run, independent of tool names. Handle tracked, untracked, deleted, and non-git files. Separate attempted paths from observed changes in the UI and report.

### 13. P2 Output caps bound context but not process memory or lifetime

Source-confirmed. [shell.go](../internal/tools/shell.go) buffers all output before applying the 48 KB cap. Verification CombinedOutput is uncapped. [BackgroundProcesses](../internal/tools/background.go) stores ongoing output in an unbounded buffer.

Normal shells and verification commands also lack the process-tree and WaitDelay treatment given to background processes. CommandContext killing a shell does not guarantee descendant cleanup; a child inheriting output handles can extend the wait. Go's [exec documentation](https://pkg.go.dev/os/exec#CommandContext) explains the cancellation and WaitDelay contracts.

**Fix:** use bounded collectors or ring buffers, stream optional spill output to disk, and apply tree termination plus bounded draining consistently. Limit aggregate tool results per model step as well: many individually capped reads can still overflow context. ReadFile's os.ReadFile also loads the complete file even for a metadata-only request.

### 14. P2 PatchFile can corrupt CRLF replacements

Reproduced. [patch.go](../internal/tools/patch.go) normalizes the file and old_content, but inserts new_content without normalizing it before restoring the file's line endings.

Replacing beta with `new\r\nline` in a CRLF file produced `new\r\r\nline`. PatchLines normalizes its replacement, so the two edit tools differ.

**Fix:** normalize both match and replacement consistently and preserve the original encoding/line-ending contract. Add byte-exact tests for LF, CRLF, BOM, and multi-line replacements. PatchLines should also use the common write-size guard.

### 15. P2 Webfetch advertises arguments its implementation rejects

Reproduced. [webfetch.go](../internal/tools/webfetch.go) declares max_bytes as a string but decodes it as *int. The schema-valid call `max_bytes: "100"` fails with a JSON type error.

For a small model, a malformed contract wastes a round trip and can trigger a retry loop. Existing tests generally use the implementation's expected type instead of validating the advertised contract.

**Fix:** declare integer and test representative arguments against each tool's schema and decoder. Prefer typed argument definitions with shared validation over hand-maintained duplicate contracts.

### 16. P2 Tool concurrency does not preserve dependencies or global ownership

Source-confirmed. [tool scheduling](../internal/agent/tool.go) runs all Concurrent calls before all Exclusive calls, even when the model listed a write before a read of that file. The read can see the previous content, while results are delivered in the original call order.

[MCPTool.Mode](../internal/tools/mcp.go) marks every remote tool Concurrent without consulting whether it mutates. Delegates share a workspace and can each run Exclusive tools; exclusivity is local to a single loop, not global across workers. Path locks protect some individual operations, but not conflicting shell commands or independent read-modify-write plans.

**Fix:** preserve call order across exclusive barriers. Default unknown MCP side effects conservatively, and make delegated file ownership explicit. Serialize overlapping work; use isolated checkouts where shared writes cannot be coordinated. On a local inference server, measure whether three simultaneous delegate requests improve wall time before making parallel inference the default.

### 17. P2 Repository search can report incomplete results as complete

Source-confirmed. [grep.go](../internal/tools/grep.go) walks the entire tree without pruning .git, .tars, node_modules, or common generated directories, ignores context cancellation, and does not inspect scanner.Err. Even after hitting the result cap it continues walking entries.

A large dependency tree or oversized line can produce slow cancellation, irrelevant matches, or silent omissions. Searching .tars can rediscover previous tool output and agent claims as if they were repository evidence.

Sensitive-read prompts apply to read_file only; grep and shell can read the same secret. That is a consistency problem in the approval UX, not a claim that the project promised adversarial isolation.

**Fix:** add ignore-aware search with an explicit include-ignored option, cancellation, early stopping, and reported partial errors. Apply sensitive-data handling consistently where it is advertised.

## Architecture and Go idioms

The project mostly follows Go idioms. Its strongest choices are small interfaces, explicit dependencies, error wrapping, leaf packages, and keeping OS-specific process handling out of the loop. Those align with the core guidance in [Effective Go](https://go.dev/doc/effective_go).

The main departure is behavioral duplication rather than syntax. cmd/agent assembles several partially overlapping configurations; TUI gate code duplicates CLI gate semantics; RunShellCommand duplicates process execution but leaves out environment and lifecycle guarantees. Consolidate these around one run configuration, one context-aware gate service, and one process runner. Avoid building a generic plugin framework to solve these three concrete problems.

The concrete tool types are easy to test. Their string result protocol is becoming a maintenance cost: failure prefixes, PASSED/FAILED, and the DELEGATE envelope carry machine meaning inside prose. Introduce a small structured ToolResult with output, error status, observed effects, and verification evidence. Format it for the model and each frontend at the edge.

Many comments explain why a decision exists, which is valuable. Some contain long incident histories and stale assertions: “four roles” where five exist, immutable “ground facts” derived from requested tool paths, and index restoration described as HEAD restoration. Keep concise invariants beside the code and move historical experiments into dedicated notes.

The conventions tests are useful but do not establish behavioral correctness. Preserve package-layer and prompt checks; prioritize integration contracts over adding more source-pattern rules.

## UX assessment

The TUI's foundation is good. Keep the consistent input zone, inline tool evidence, expanded/collapsed output, scroll preservation, and permission previews.

The biggest product problem is workflow fragmentation. The TUI cannot start mission, plan, fork, or command-line resume flows, although it can browse saved sessions. Multi-file filename mentions automatically activate mission mode in print mode but not the TUI. “Compare a.go and b.go” can trigger a planning pipeline even though it is a read-only question. Conversely, omitted extensions and Windows path spellings limit the routing heuristic.

Prefer explicit direct and mission choices with a visible recommendation. Keep the same execution engine and outcome presentation across frontends. A user should not have to switch interfaces to use the project's strongest reliability feature.

Other changes worth making:
- Empty Enter should do nothing; quitting already has explicit commands and keys.
- Escape should stop a run while preserving the chat. Keep its idle behavior consistent.
- Allow users to draft or queue a follow-up during inference; local generation can be slow.
- “Always for this run” should actually expire at the end of the run. The TUI map persists across turns/new chats, while CLI “always” has no comparable memory.
- Show a final outcome with changed files, check commands and verdicts, unresolved work, and the exact resume target. A narrative “run finished” is insufficient.
- The tool-card failure detector checks only a leading error prefix, but failures with compiler output append the error afterward. Use structured error status to style failures correctly.
- Existing non-image @file references error rather than attaching code. Either support source attachments or explain that @ accepts images in the input affordance.
- Make model/backend/context identity and the absence of sandboxing visible during setup. A status command alone is weak onboarding.

These are implementation and interaction findings. Contrast, density, narrow-terminal layout, and accessibility need a separate live visual pass.

## Evaluation and model strategy

The 623 existing test functions and high core coverage are substantial. Baseline coverage was 90.8% for agent and 84.4% for TUI, but only 23.3% for cmd/agent and 11.0% for cmd/eval. The integration bugs cluster where entry-point coverage is weakest.

Passing the race detector does not catch stale events or incorrect sequencing. The TUI reproduction is a semantic race, not necessarily an unsynchronized memory access. Add lifecycle and permission parity tests across actual entry points.

The eval suite is a useful regression instrument, but 16 dry-validated probes are not evidence of coding quality. Several stress a preferred tool choice rather than task success. Keep those as protocol tests; add larger behavioral tasks with independent tests, preservation checks, realistic repositories, and negative assertions against unrelated edits. Mechanize git ambiguity and ask_user cases that remain write-ups only.

For each deployed model/backend/configuration, report:
- Functional success and preserved unrelated behavior.
- False success, cancellation success, and denied-operation execution rates.
- Attempted runs, completed runs, infrastructure errors, and skips separately.
- Median and tail elapsed time, prompt/generated tokens, retries, and repair work.
- Direct versus mission results under the same tasks and acceptance criteria.
- With and without leak recovery, hard repeat refusal, compaction, and verification nudges.

Do not remove weak-model guardrails merely because a stronger model passed a few cases. Equally, do not keep adding prompt exceptions without evidence that the combined system improves. The current design has accumulated many responses to individual failures; an ablation suite should decide which mechanisms earn their complexity.

Whether Muse Spark 1.3 is the right implementation assistant is not answerable from this repository. Whether a particular local inference model works well on your 12 GB and 8 GB cards also needs measured model/quantization/context configurations. TARS's own CPU footprint is unlikely to be the primary inference bottleneck; server queueing, context size, and simultaneous workers deserve measurement.

## Security and persistence judgment

The documented absence of a sandbox is acceptable for a personal supervised tool. Keep that boundary explicit. Shell execution, symlink traversal, and repository prompt injection are expected within the stated trust model; they are not new vulnerabilities just because they can touch user-owned files.

However, explicit deny, credential scrubbing, public-network-only fetches, and rollback are narrower promises that the harness can and should uphold. Findings 1–5 are failures of those promises.

Persistence is recoverable in concept: atomic snapshot replacement plus a JSONL fallback is sensible. saveState silently ignores failures, so the operator can be told to resume from a state that was not saved. Emit a visible persistence warning with the last confirmed save. The log appends the complete growing history at every save, amplifying disk use and retaining tool output/possible secrets. Define retention and redaction, and consider incremental events plus periodic checkpoints.

AGENTS.md is mentioned in SECURITY.md but there is no deterministic loader in the code examined. Skills are suggested through prompts and workspace paths rather than discovered and injected by a harness. That can be a deliberate scope choice, but document it clearly. If repository instructions are part of the product contract, load them with defined precedence, bounded size, provenance, and persistence across compaction.

## Recommended sequence

1. Enforce policy independently of gates; preserve run configuration in mission mode; unify process environment handling; fix fetch destination validation. Upgrade the Go toolchain.
2. Make cancellation and TUI run identity correct. Add stop/EOF tests at every suspension point.
3. Implement pre-run rollback and workspace-delta tracking. Tie completion and verification to current observed state.
4. Fix SSE termination, schemas, CRLF handling, scheduler ordering, and search completeness.
5. Unify frontend workflows and publish repeated real-model eval results before broadening the tool set.

This sequence preserves the project's good design while making its observable promises dependable.


## Remediation completed in the working tree

The review above describes the original revision. The subsequent implementation
addresses all 17 numbered findings:

- Policy is unconditional and fail closed. Direct, mission, delegated, RPC and
  TUI runs share configuration; model-generated mission checks also obey policy.
- Public fetches validate redirects and resolved destinations, dial validated IPs,
  and ignore environment proxies. Shells and checks share scrubbed environments,
  bounded output, cancellation and process-tree cleanup.
- Pre-run archives retain working files, staged state and pre-existing untracked
  files. Restore validates archives before applying them; preview is read-only.
  Later edits invalidate verification and read caches. Actual workspace changes
  include shell, MCP and delegated effects.
- Gates use active contexts, fail after input EOF, preserve submitted answers and
  reject duplicate responses. TUI interruption drains the old run before another
  starts, with completion ordered behind its events.
- The minimum toolchain is Go 1.26.6. The transitive x/text dependency is updated
  to v0.39.0. CI uses go.mod and runs the race detector on Windows and Linux.
- Incomplete/malformed SSE is rejected; false file-completion claims are refused;
  file reads and process logs use bounded memory; patches preserve CRLF and enforce
  write limits; webfetch's argument schema matches its decoder.
- Reads run in consecutive batches separated by ordered mutation barriers.
  Delegation and MCP calls are exclusive in the shared workspace. Search respects
  Git ignores, cancellation, sensitive paths and partial errors.

The cleanup also adds deterministic ancestor/workspace AGENTS.md loading,
current instructions on resume, visible persistence errors and bounded session
log rotation. Tool results carry typed failure status separately from prose.
Mission selection is explicit. The TUI supports plan, mission and saved-history
flows, accepts drafts and one queued follow-up, preserves input around gates,
and treats empty Enter as a no-op. Outcomes expose observed files, check evidence
and the resume target. CLI errors now unwind cleanup before exiting.

The eval suite now mechanizes all 19 scenarios, including seeded Git history
and scripted clarification. Rollback is tested without a cleanup command masking
its failures. Documentation and model guidance match the execution contracts.

Validation on Windows: full tests and full race suite passed; go vet, go build,
19-probe dry validation and git diff --check passed. Govulncheck reports no
vulnerabilities after both upgrades. Targeted regressions cover policy denial,
mission-check denial, gate closure, verification invalidation, ordered scheduling,
actual file effects, dirty/staged rollback, network destination enforcement,
stream termination, CRLF edits and typed TUI error status.

Live model quality, inference performance, a visual terminal session and Linux
runtime behavior remain unmeasured locally. CI is configured for Linux checks;
that configuration is not a claim that they have run. Model-authored mission
checks remain as strong as their acceptance criteria. Shell execution remains
inside the user's account boundary. Ignored files, .tars state and Git history
changes are outside checkpoint restoration; archives and debug traces need
operator-managed retention.
