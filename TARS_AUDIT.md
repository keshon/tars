# TARS Codebase Audit

## Overview
TARS is a local agentic system designed around a single, robust execution loop. The architecture prioritizes observability and reliability by measuring actual filesystem and tool effects rather than relying on the LLM's self-reported progress.

## Core Architecture

### The Agent Loop (`internal/agent`)
The heart of the system is the `Agent.run` loop. It follows a strict sequence per step:
1. **Chat**: Communicate with the LLM.
2. **Recover**: Extract "leaked" tool calls that were emitted as plain text.
3. **Bookkeeping**: Update step counts, token usage, and handle context compaction.
4. **Dispatch**: Execute tool calls based on their concurrency mode (`Concurrent` vs `Exclusive`).
5. **Interject**: Apply "nudges" if the agent appears stuck or is approaching budget limits.
6. **Persist**: Save the session state and history.

### Key Mechanisms

#### 1. Repeat Detection & Guardrails
To prevent infinite loops and wasted tokens, TARS implements several hard and soft guards:
- **Idempotent Guards**: If an idempotent tool (like `read_file`) is called with the same arguments and nothing has changed in the workspace, the call is refused with an error.
- **Write Guards**: Prevents redundant `write_file` calls to the same path within a single run.
- **Failure Thresholds**: If a specific tool call fails multiple times without any workspace mutation, it is blocked to force a change in strategy.
- **Stuck/Exploratory Counters**: Tracks consecutive steps with no progress to trigger escalating nudges.

#### 2. Concurrency Model (`ToolMode`)
Tools are categorized into two modes:
- **`Concurrent`**: Safe to run in parallel (e.g., pure reads, independent subtasks).
- **`Exclusive`**: Must run alone to prevent race conditions (e.g., `write_file`, `patch_file`, `run_shell`).

#### 3. Mission Management (`internal/mission`)
Missions are state machines that guide agents through phases: `explore` $\rightarrow$ `plan` $\rightarrow$ `execute` $\rightarrow$ `verify`. 
- **Verification**: Subtasks include explicit checks (e.g., `file_exists`, `shell`) to ensure work is actually done.
- **Fix & Replan**: Failed checks trigger a "fix" worker or a full replan, providing a structured way to recover from errors.

#### 4. Role-Based Access Control (`internal/roles` & `internal/permission`)
Agents are constructed with specific toolsets to enforce behavior:
- **Inspector**: Read-only access.
- **Subagent**: Full tools, but cannot delegate.
- **Worker**: Full tools, cannot delegate.
- **Interactive**: Full tools plus delegation and user interaction.

### Package Map

| Package | Responsibility |
|---|---|
| `internal/agent` | The core execution loop and tool registry. |
| `internal/llm` | Backend interfaces (OpenAI, Llama.cpp, KoboldCPP) and grammar handling. |
| `internal/tools` | Concrete implementations of all available tools. |
| `internal/mission` | High-level task planning, execution, and verification logic. |
| `internal/permission` | Policy enforcement for tool calls. |
| `internal/workspace` | Path resolution and filesystem boundary enforcement. |
| `internal/session` | Append-only logging of agent history and state. |

## Security & Reliability
- **SSRF Protection**: `webfetch` is validated.
- **Workspace Boundary**: `internal/workspace` provides a layer of protection for file operations.
- **Atomic Writes**: State saving uses a temporary file + rename pattern to prevent corruption.
- **Measured Progress**: Completion is verified via tool results and filesystem state, not model text.

## Known Limitations
- **Shell Sandbox**: `run_shell` is limited by working directory but is not a full sandbox.
- **Plan Dependency**: The quality of mission execution is heavily dependent on the initial plan generated by the model.
